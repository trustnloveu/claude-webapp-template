사용자의 요청을 바로 실행하지 말고, 먼저 구체화해서 요청서로 만든다.

## 사용자 입력
$ARGUMENTS

## 진행 순서

0. **원문 기록**: 사용자 입력을 고치지 않고 그대로 남긴다. 프로젝트 요구사항이면 docs/planning/requirements.md "원문"에, 기능 단위 요청이면 요청서 맨 위에 둔다(파일 저장은 사용자가 원할 때).

1. **맥락 읽기**: `docs/PIPELINE.md`로 현재 단계를 확인하고, 요청과 관련된 문서(`docs/planning/idea.md`, `docs/planning/requirements.md`, `specs/`, `docs/design/ux.md`, `docs/design/README.md`, `docs/engineering/tech-stack.md`, `docs/decisions/`, 관련 코드)를 읽는다. 문서에 이미 정해진 내용은 질문하지 않고 채운다.

2. **분해**: 입력을 `docs/guide/request-guide.md`의 8가지 요소(목표, 배경, 범위, 제외, 완료 조건, 제약, 참고, 모르는 것)로 나눈다. 입력이 흩어진 생각이면 같은 주제끼리 묶어서 나눈다.

3. **라운드 질문**: 비어 있거나 여러 가지로 해석되는 요소를 결정 트리(한 결정이 정해져야 다음 결정을 물을 수 있는 구조)로 보고 라운드로 묻는다.
   - 한 라운드에는 지금 답할 수 있는 질문만 묻는다. 다른 질문의 답에 따라 달라지는 질문은 다음 라운드로 미룬다. 순서는 목표 → 범위 → 완료 조건이 먼저다.
   - 질문마다 번호를 붙이고 선택지 2~3개와 각 장단점·영향을 한 줄로 붙인 뒤, 추천 답을 적는다. "네"라고 하면 추천 답을 받아들이는 것으로 읽히게 쓴다.
   - 문서·코드에서 찾을 수 있는 사실은 묻지 않고 직접 찾는다. 사람에게는 결정만 묻는다.
   - 답을 받으면 트리를 다시 보고 다음 라운드를 묻는다. 모든 갈래가 정해지거나 "모르는 것"으로 넘어가 아무것도 말없이 추정한 채 남지 않을 때 끝낸다.
   - 기능 아이디어나 새 요구사항이면 "하지 않을 것"과 "제품 원칙"(docs/planning/idea.md)도 묻는다. 이미 채워져 있으면 그것과 충돌하는지만 확인한다.
   - 완료 조건이 "확인해 줘", "잘 되게"처럼 판정할 수 없으면 판정 가능한 검사로 바꾼 선택지를 제시한다.
   - 사용자가 "모름"이라고 하면 더 캐묻지 말고 "모르는 것"에 넣는다. 단, 작업을 막는 항목이면 그렇다고 알린다.
   - 문서와 충돌하는 요청(예: 스펙의 Won't 기능, 현재 단계 밖의 작업)이면 먼저 알린다.

4. **요청서 제시**: 아래 형식으로 정리해서 보여 주고 확인을 받는다. 출처가 문서인 항목은 경로를 붙이고, Claude가 추정한 항목은 `(추정)`을 붙인다.

   ```text
   [단계]
   [목표]
   [배경]
   [범위]
   [제외]
   [완료 조건] 실행하거나 대조해서 통과·실패를 가릴 수 있는 검사로 쓴다 (예: "OO 테스트 통과", "인수 기준 3개를 화면에서 확인")
   [제약]
     - 재량: Claude가 스스로 바꿔도 되는 것(도구·순서·세부 방식) / 바꾸기 전에 물어야 하는 것
   [참고]
   [모르는 것]
   ```

5. **다음 행동 제안**: 확인을 받으면 `/plan-work`로 단계 판정을 제안한다. 요청이 새 요구사항이거나 스펙 변경을 포함하면 "기획(planner 분석)부터", 화면 변경을 포함하면 "UI/UX(designer)부터" 필요하다고 함께 알린다. 사용자가 진행하라고 하기 전에는 파일을 수정하지 않는다.

## 지킬 것
- 라운드가 3번을 넘거나 한 라운드 질문이 5개를 넘으면, 범위를 나눠 여러 요청으로 쪼개자고 제안한다.
- 결정할 사항(MVP 범위, 스택, 디자인 승인 등)은 사용자에게 맡기고, Claude는 선택지와 근거만 준다.
- 요청서가 확정되면 사용자가 원할 때 `docs/requests/<YYYY-MM-DD>-<짧은-이름>.md`로 저장한다.
