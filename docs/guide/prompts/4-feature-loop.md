# 4단계. 기능 구현 루프

> 대상: 사람

기능 하나마다 5-1~5-6을 반복합니다. 도구: Spec Kit(tasks), Superpowers TDD, Figma MCP, UI UX Pro Max, Playwright, `/code-review`

## 역할로 진행하기 (권장)
기능마다 기획 확인 → 디자인 확인 → 계획 → 구현 → 검증 순서로 진행합니다. [프로젝트 구성원](../roles.md)의 흐름을 따릅니다.
아래 개별 프롬프트는 에이전트에게 건네는 작업 지시서의 내용이 되거나, 에이전트 없이 직접 진행할 때 씁니다.

| 순서 | 담당 | 명령·확인 | 안 되면 |
|---|---|---|---|
| 요청 정리 | 총괄 | `/refine [기능 ID] [기능명] 구현` | — |
| 기획 확인 | 총괄 → planner | 스펙·인수 기준이 승인됐나 | 1단계 기획(1-planning-spec.md)으로 |
| 디자인 확인 | 총괄 → designer | 화면 상세가 있고 디자인 상태가 "승인"인가 | 2단계 UI/UX(2-uiux.md)로 |
| 계획 | 총괄 | `/plan-work` → **계획 승인** | — |
| 백엔드 | 04 backend-dev | 메인 세션이 지시 | — |
| 프론트엔드 | 03 frontend-dev | 메인 세션이 지시 | — |
| 검증 | 05 qa + 06 reviewer + 02 designer + 01 planner (+ 화면이면 09 a11y-auditor, 보안 변경이면 07 security-auditor, 보안 핵심 "대"면 08 appsec-engineer) | 메인 세션이 동시에 지시 | 원인이 기획·디자인이면 그 단계로 |
| 마무리 | 사람 | **결과 승인** → PR → 병합 | — |

## Figma → 코드 (원본 ⑲) — 5-5
```text
Figma 프레임 [URL]을 Figma MCP로 읽어 apps/web에 구현해 줘.
먼저 디자인과 현재 코드 구조를 분석해 구현 계획(새 컴포넌트, 재사용할 컴포넌트, 수정 파일)을 보여 주고 승인을 받아.
디자인 토큰만 쓰고 여백·폰트·색·크기를 시안과 맞춰. 반응형과 접근성(키보드, 대비, 라벨)을 지켜.
디자인을 임의로 바꾸지 말고, 구현이 어려운 부분은 먼저 말해.
```

## 프론트엔드 기능 (원본 ⑳) — 5-5
```text
[기능 ID] 기능을 apps/web에 구현해 줘. 인수 기준: [스펙에서 복사]
컴포넌트 구조, 인터랙션, 상태 관리, API 연결(packages/shared 타입), 로딩·빈 상태·에러 상태, 입력값 검증, 반응형.
관련 파일만 수정하고, 인수 기준마다 테스트를 써.
```

## 백엔드 API (원본 ㉑) — 5-4
```text
OpenAPI의 [operationId]를 apps/api에 TDD로 구현해 줘.
실패하는 테스트를 먼저 보여 주고, 입력 검증, 비즈니스 로직 분리, DB 연동, 예외 처리, 인증·권한, 상태 코드를 구현해.
응답·에러 형식은 apps/api/CLAUDE.md를 따르고, 테스트를 고치거나 건너뛰어 통과시키지 마.
```

## AI 기능 연동 (원본 ㉒)
```text
[AI 기능 설명]을 추가하려고 해. 구현 전에 설계안부터 보여 줘.
1. 모델·API 선택과 이유  2. 프롬프트 설계  3. 입력·출력 데이터 구조  4. 서버에서만 API 키 사용
5. 스트리밍 여부  6. 오류·재시도·타임아웃  7. 사용량·비용 상한  8. 응답 품질 검증 방법(평가 예시 5개 이상)
승인하면 백엔드 API로 구현하고, 예상 월 비용을 docs/decisions에 ADR로 남겨.
```

## 디자인 검수 (원본 ㉔) — 5-6
```text
Playwright로 [화면 ID]를 데스크톱·모바일 크기로 캡처하고 Figma 프레임과 비교해 줘.
레이아웃, 위치, 크기·여백, 색, 폰트, 버튼·입력창, 반응형, 인터랙션 순으로 차이를 표로 정리하고
심각도(높음/중간/낮음)를 붙여. 수정은 내가 우선순위를 정한 뒤에 해.
```

## 5-6 마무리
```text
/code-review를 실행하고, 지적 사항을 고친 뒤 공통 원칙의 "자체 검증"과 "문서 갱신"을 수행해.
PR 템플릿을 채워 PR을 만들고 PIPELINE.md 기능 표를 갱신해.
```
