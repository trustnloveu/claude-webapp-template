# 요청 작성 가이드

> 대상: 사람

Claude에게 일을 맡길 때, 머릿속 생각을 빠짐없이 전달하기 위한 가이드입니다.
요청이 짧거나 막연해도 괜찮습니다. `/refine <요청>`을 쓰면 Claude가 빠진 부분을 질문으로 채워 줍니다.

## 1. 좋은 요청의 8가지 요소

| 요소 | 스스로 던질 질문 | 빠지면 생기는 일 |
|---|---|---|
| 목표 | 무엇이 되면 끝인가? | Claude가 범위를 마음대로 정함 |
| 배경 | 왜 필요한가? 누가 쓰나? | 엉뚱한 방향으로 최적화 |
| 범위 | 이번에 무엇을 포함하나? | 너무 많이 하거나 너무 적게 함 |
| 제외 | 이번에 무엇은 하지 않나? | 요청하지 않은 파일까지 수정 |
| 완료 조건 | 끝났다는 걸 어떻게 확인하나? | "다 했어요"를 검증할 수 없음 |
| 제약 | 지켜야 할 기술·디자인·비용·일정 조건은? | 정한 스택·토큰을 무시 |
| 참고 자료 | 관련 문서, 시안(HTML·Figma), 기존 코드, 예시 서비스는? | 이미 정한 내용을 다시 만듦 |
| 모르는 것 | 아직 정하지 못한 부분은? | Claude가 추측으로 채움 |

8개를 모두 채울 필요는 없습니다. **목표, 범위, 완료 조건** 세 가지만 있어도 결과가 크게 달라집니다.
모르는 것은 "모름"이라고 적는 것이 비워 두는 것보다 낫습니다. 그래야 Claude가 추측하지 않고 질문합니다.

## 2. 요청서 양식

복사해서 빈칸을 채웁니다. 모르는 칸은 `모름`이라고 적습니다.

```text
[단계] <PIPELINE 단계. 예: 5. 기능 루프 / 5-5 프론트엔드>
[목표] <이 작업이 끝나면 무엇이 가능해지나>
[배경] <왜 필요한가, 누가 쓰나>
[범위] <포함할 것>
[제외] <이번에 하지 않을 것>
[완료 조건] <어떻게 확인하나. 예: 스테이징에서 가입 → 로그인 → 로그아웃이 된다>
[제약] <기술·디자인·비용 조건>
[참고] <문서 경로, 시안 파일(docs/design/mockups/) 또는 Figma 링크, 기능 ID, 비슷한 서비스>
[모르는 것] <정하지 못한 부분>
```

## 3. 나쁜 예와 좋은 예

**아이디어 단계**

- 나쁜 예: `운동 기록 앱 만들고 싶어. 아이디어 정리해 줘.`
- 좋은 예:
  ```text
  [목표] docs/planning/idea.md를 채울 수 있을 만큼 아이디어를 구체화
  [배경] 헬스장에 다니는 직장인이 운동 기록을 꾸준히 못 남기는 게 불편함(내 경험)
  [범위] 문제, 타깃, 경쟁 서비스, 차별화
  [제외] 기능 목록과 기술 스택은 아직 다루지 않음
  [완료 조건] "우리는 ~가 ~를 ~로 해결하게 돕는다" 한 문장이 나옴
  [모르는 것] 수익 모델, 모바일 앱이 필요한지 여부
  ```

**기능 개발 단계**

- 나쁜 예: `로그인 만들어 줘.`
- 좋은 예:
  ```text
  [단계] 5. 기능 루프, F-003 로그인
  [목표] 가입한 사용자가 이메일과 비밀번호로 로그인할 수 있다
  [범위] 로그인 API, 로그인 화면(S-002), 로그인 유지
  [제외] 소셜 로그인, 비밀번호 찾기(다음 기능)
  [완료 조건] 스펙 F-003의 인수 기준 3개를 모두 통과, 스테이징에서 직접 확인
  [제약] 인증 방식은 ADR-003을 따름
  [참고] specs/001-mvp, docs/design/mockups/S-002.html
  [모르는 것] 로그인 실패 5회 시 잠금이 필요한지
  ```

**수정 요청**

- 나쁜 예: `화면이 이상해. 고쳐 줘.`
- 좋은 예:
  ```text
  [목표] 모바일에서 S-004 목록 화면의 카드가 잘리지 않게
  [범위] apps/web의 카드 목록 컴포넌트
  [제외] 데스크톱 레이아웃, 다른 화면
  [완료 조건] 375px 폭에서 Playwright 스크린샷이 결정된 시안과 일치
  [참고] 문제 스크린샷 첨부
  ```

## 4. 단계별로 특히 챙길 요소

| 단계 | 특히 챙길 요소 | 이유 |
|---|---|---|
| 1. 아이디어 | 배경, 모르는 것 | 경험과 가정을 구분해야 이후 단계가 흔들리지 않음 |
| 2. 스펙 | 범위, 제외 | MVP가 커지는 것을 막음 |
| 3. 설계 | 제약, 참고 | 비용·학습 난이도 같은 조건이 선택을 좌우함 |
| 4. 뼈대 | 제외 | 기능을 넣고 싶은 유혹을 막음 |
| 5. 기능 루프 | 완료 조건, 참고(기능 ID, 시안) | 인수 기준과 시안이 있어야 검증 가능 |
| 6. 출시 | 완료 조건 | 체크리스트로 끝을 판단 |

## 5. 생각이 정리되지 않을 때

머릿속에 생각이 흩어져 있으면 정리하지 말고 그대로 쏟아 놓습니다.

```text
/refine 아직 정리가 안 됐는데 생각나는 대로 적을게.
<떠오르는 대로 나열. 문장이 아니어도 됨>
```

Claude가 흩어진 내용을 8가지 요소로 나누고, 비어 있는 부분만 질문합니다.
